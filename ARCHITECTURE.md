# agenda — Structure & Design

A paper-planner-style app: weekly and monthly spreads rendered from JSON page templates, with
rich-text day entries (TipTap) and a freehand drawing layer (tldraw) on every page. It is
**local-first**: everything the user does is stored in a SQLite database on their device and the
app never needs a network connection. Online features (external calendar sync, sharing templates,
syncing between devices) are planned as opt-in additions on top of that, not as a requirement.

The whole application is TypeScript/React. A thin Tauri shell provides the window and SQLite on
desktop; in a plain browser the same code runs on sql.js. The Rust backend that preceded this
design still sits in `apps/agenda_rust` until the new shell has been exercised, and is no longer
built by anything.

---

## 1. Workspace layout

Yarn 1 workspaces (`apps/*`). The Rust shell is a standalone Cargo package.

| Path | Role |
|---|---|
| `apps/frontend` | The app: React UI, the TypeScript domain layer, the storage layer, the schema, all tests. |
| `apps/desktop/src-tauri` | Tauri 2 shell: one window plus `tauri-plugin-sql`. About sixty lines of Rust. |
| `apps/desktop/scripts/import-legacy-db.mjs` | One-off import of the old Rust backend's SQLite file into the new database. |
| `apps/agenda_rust` | Retired Loco/SeaORM backend and old Tauri shell. Kept only as a reference; delete once the new shell is trusted. |
| `TS_MIGRATION_PLAN.md` | The plan this layout follows, with the "behaviours to preserve" list. |

## 2. Runtime architecture

```
            React routes (TanStack Router) ──► loaders call domain functions directly
                              │
                              ▼
            src/domain/*   pages.ts (find-or-build), repositories, calendar math
                              │  Database interface: select(sql, params) / execute(sql, params)
                              ▼
     ┌──────────────────────────────────────┐   ┌──────────────────────────────────────────┐
     │ adapters/tauriSql.ts (inside Tauri)  │   │ adapters/sqljs.ts (plain browser, vitest) │
     │ @tauri-apps/plugin-sql → sqlx →      │   │ sql.js (SQLite in wasm), image saved to   │
     │ %APPDATA%\com.agenda.dev\agenda.db   │   │ IndexedDB 500 ms after each change        │
     │ migrations applied by the Rust shell │   │ migrations applied by migrate.ts          │
     └──────────────────────────────────────┘   └──────────────────────────────────────────┘
```

- `getDb()` (`src/db/index.ts`) decides with `isTauri()` and memoises one connection. `main.tsx`
  awaits it before mounting, so a storage problem is reported on screen instead of inside a loader.
- There is no IPC protocol and no HTTP API. The desktop shell registers the SQL plugin with the
  migration list and nothing else; the frontend talks to SQLite through the plugin's `select` and
  `execute` commands.
- Nothing is fetched at runtime: the Aref Ruqaa font is bundled through `@fontsource`, tldraw's
  icons, fonts and translations through `@tldraw/assets` (excluded from Vite pre-bundling because
  its `?url` imports need Vite's own pipeline), and the desktop CSP allows only `'self'`.

## 3. Data model

Schema in `apps/frontend/src/db/migrations/0001_init.sql`. Conventions on every table:

- `id` is a UUID v4 string minted by the app (`domain/ids.ts`), never by the database.
- `created_at` / `updated_at` are ISO-8601 UTC strings; calendar dates (`page_date`, `entry_date`)
  are `YYYY-MM-DD` strings; JSON columns are TEXT; booleans are 0/1.
- `deleted_at` (soft delete, every read filters it) and `version` (bumped on every update) exist on
  every user-data table so that device sync can be added later without a schema rewrite.

| Table | Purpose | Notable |
|---|---|---|
| `profiles` | Local profile, replaces the old auth user. Migration inserts a well-known default (`00000000-0000-4000-8000-000000000001`). | `name`, `settings` JSON |
| `planners` | One planner book | `planner_settings` JSON: `holiday_countries`, `holiday_regions`, `metadata.default_styles["week-start-day"]`, month colours, base dimensions |
| `page_templates` | Declarative layout tree for a page kind | `template_type` in daily, weekly, monthly, custom, weekly_left, weekly_right, extra; `is_default`; `content` JSON `{metadata, structure}`; `schema_version` |
| `pages` | A materialised template for one period | `page_type` weekly/monthly, `period_identifier` (`MM_YYYY`, or `W_YYYY_l`/`_r` with the week not zero-padded), `page_date`; `UNIQUE(planner_id, page_type, period_identifier)` |
| `planner_entries` | One editor slot on a page | `tiptap_id` (slot), `entry_date`, `content` = TipTap JSON document; `UNIQUE(page_id, tiptap_id)` |
| `tldraw_snapshots` | The drawing layer of a page | `document` = the `document` half of tldraw's `getSnapshot()`; one row per page (`UNIQUE page_id`) |
| `events` | Calendar events with recurrence, plus `external_id` / `calendar_id` for future sync | no application code yet |

The UNIQUE constraints are what let every write be a single `INSERT ... ON CONFLICT ... DO UPDATE`
or `INSERT OR IGNORE`, which matters because the Tauri SQL plugin has no transaction spanning calls.

## 4. Domain logic

### Page builders (`domain/pages.ts`)

`loadWeeklyPage(db, plannerId, weekId)` and `loadMonthlyPage(db, plannerId, monthId)` reproduce the
old Rust find-or-build behaviour (captured in `domain/__fixtures__` and asserted by
`pages.test.ts` for every fixture):

1. Load the planner (`'invalid planner_id (expected UUID)'`, `'planner not found'`).
2. Resolve the period. Weeks: `W_YYYY_[lr]`, normalised so week 0 rolls to the last ISO week of the
   previous year and a week past `weeksInYear` rolls to week 1 of the next; the window starts at
   the ISO Monday stepped backwards to the planner's week-start day. Months: `MM_YYYY`, one-digit
   months accepted and normalised.
3. Find the page by (planner, type, normalised id) or create it from the planner's default template
   of the matching type (`'Default template not found'` / `'Default monthly template not found'`),
   race-free via `INSERT OR IGNORE` and reselect.
4. Load the period's entries grouped by date and the page's snapshot.
5. Compute calendar data: holidays, moon phases, per-day template data, the seven-letter
   `daysOrder`, and for the right page the two 42-cell mini calendars and prev/next week ids.

The returned shapes (`WeeklyPage`, `MonthlyPage` in `domain/types.ts`) keep the key names the React
components already read (`page_id`, `tldraw_snapshots`, `weekData`, `user_id` on the template).

### Calendar modules (`domain/calendar/`)

- `weeks.ts` / `months.ts`: ISO week math implemented on `dates.ts`, ids, ranges, navigation,
  `weekIdForDate(date, side, weekStartIndex)` for "this week".
- `grids.ts`: `daysOrder`, 42-cell month grids, `calendarsForWeek`.
- `moon.ts`: phase sampled at 12:00 UTC, eight named buckets, emoji emitted only on the day the
  phase changes within the requested range. The suncalc 1.x formulas are inlined because the npm
  `suncalc` resolved to a 2.x release whose ephemeris disagrees with the captured fixtures.
- `holidays.ts`: `date-holidays`, national public holidays by default (`holiday_countries`, with
  `uk` → `GB`), sub-national ones opt-in through `holiday_regions` such as `US-IL`, multi-day
  holidays expanded per day. This is narrower than the Rust build, which merged every US state.

### Repositories

`profiles.ts`, `planners.ts`, `templates.ts`, `entries.ts`, `snapshots.ts`: db-first functions
(`listPlanners(db)`, `createPlanner(db, input)`, `upsertEntry(db, input)`, `saveSnapshot(db,
input)`, …), validation with the same error strings as the Rust models, JSON parsed on read.
`createPlanner` seeds the three bundled default templates so a fresh install renders pages.

## 5. Storage layer

`src/db/Database.ts` is the whole contract: `select`, `execute`, `close`, positional `?` params of
type string | number | null. Rules: single-statement writes, JSON as strings, dates as strings.

- **Desktop** (`adapters/tauriSql.ts`): `Database.load('sqlite:agenda.db')` from
  `@tauri-apps/plugin-sql`; the file lives in the app config directory
  (`%APPDATA%\com.agenda.dev\agenda.db` on Windows); the Rust shell embeds `0001_init.sql` with
  `include_str!` and the plugin applies it at load.
- **Browser** (`adapters/sqljs.ts` + `persistence/indexedDb.ts` + `migrate.ts`): in-memory sql.js
  database seeded from the image stored under the IndexedDB key `agenda.sqlite`, saved back at most
  once per 500 ms after a write (and on `pagehide`). Saving is armed only after migrations so a
  failed read can never clobber a stored image. Dev-only durability; the desktop never uses it.
- **Tests** (`testing.ts`): `createTestDb()` gives every test a fresh migrated database.

## 6. Frontend wiring

- Routes call domain functions in their loaders and pass results straight to the renderers.
- `Tiptap.tsx` / `TiptapMonthly.tsx` load their slot with `getEntry` and save `editor.getJSON()`
  with `upsertEntry`, debounced 2 s and flushed on unmount; the entry date comes from the day
  section (or the week start for the right page's free text boxes; monthly cells use their own day,
  formatted from local components, which fixes an old UTC off-by-one).
- `TLDrawComponent.tsx` loads `tldraw_snapshots[0].document_data` into a store and saves the
  document half of each snapshot with `saveSnapshot`, debounced 350 ms and flushed on unmount. It
  takes `pageId`; the monthly page now has a drawing layer too.
- The drawing layer covers the page by default; "Disable TLDraw" in tldraw's quick actions hides
  it for typing, and the power icon brings it back.
- `PageTemplateEditor.tsx` saves with `saveTemplate` and picks the planner from a dropdown.
- `/` lists planners with links to this week and this month; `/planners/create` seeds templates
  and lands on the current week; `/users/create` creates a profile (name only).

## 7. Build, run, test

```sh
yarn install                        # from the repo root
yarn dev                            # desktop app: starts Vite on :3000 and the Tauri shell (apps/desktop)
yarn build                          # desktop bundle
yarn --cwd apps/frontend dev        # the app in a plain browser on sql.js, http://localhost:3000
yarn test                           # vitest: storage, calendar, repositories, fixture parity
yarn smoke                          # Playwright smoke test on the installed Edge (headed: SMOKE_HEADED=1)
yarn --cwd apps/frontend typecheck:domain
node apps/desktop/scripts/import-legacy-db.mjs [--dry-run]   # after the desktop app has run once
```

- The Tauri shell is a standalone Cargo package; `cargo build` in `apps/desktop/src-tauri` builds
  it. Windows links with `rust-lld` (`.cargo/config.toml`).
- Parity fixtures were captured from the Rust binary; the capture script lives outside the repo
  (see `src/domain/__fixtures__/README.md`). Regenerate only while `apps/agenda_rust` still exists.

## 8. Divergences from the Rust build and known rough edges

- Holidays: national only by default (see section 4); the Rust build merged every US subdivision.
- `4_2025` style month ids are accepted; Rust rejected them.
- Monthly pages now receive `monthData` (holidays, moon phases, days); the Rust IPC layer dropped it.
- Entries without a date are rejected; Rust silently stamped today.
- Entry content is TipTap JSON; the old rows held HTML strings (the import converts them).
- The `extra` template type is allowed, matching the editor.
- `public/images/monthly/monthly-bg.svg`, referenced by the monthly template, does not exist.
- The index page, planner creation and profile creation are functional but unstyled.
- The `about` route and the unused CSS files (`test.css`, `fakecss.css`) are leftovers.
- `apps/agenda_rust` is unused and should be deleted (or its Loco server pieces parked for the
  future sync service) once the new shell has been used for a while.
